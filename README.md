**Does a proposed work area conflict with existing utility infrastructure — and which jurisdiction is
it in?** A **fully static, client-side** GIS conflict-analysis dashboard: tabular and spatial SQL,
precision geometry, and the map all run in the browser. No backend, no database server — so it hosts
as a static site on GitHub Pages.

**▶ [Live demo](https://the-snowmen.github.io/GIS-Conflict-Dashboard/)**

[![GIS Conflict Dashboard — a walkthrough: H3 conflict-index screening and drill-down, a flagged ticket's buffer conflict and why-dossier, and the live conflict rule recomputing the flagged tally](docs/demo.gif)](https://the-snowmen.github.io/GIS-Conflict-Dashboard/)

> **Note.** A personal project. The basemap layers are public-domain (EIA transmission lines, Census
> counties); the tickets and areas of interest are **synthetic**, generated by the build script — see
> [`DATA_SOURCES.md`](DATA_SOURCES.md).

## What it does

- **Conflict analysis** — drop a work point (geodesic meter buffer) or draw an AOI polygon; the
  intersecting facilities (`ST_Intersects`) and containing county (`ST_Within`) are computed live, with
  an adjustable buffer radius.
- **Interactive conflict rule** — an editable owner/status rule (with one-click presets) sets what
  counts as a conflict. Changing it recolors the network **and recomputes the flagged tally live**
  across the whole dataset, while every flagged ticket keeps a **why-dossier**: the conflicting
  facilities itemized and ranked nearest-first, each row clickable to inspect, with intake-vs-live counts.
- **Ticket evidence** — searchable, filterable work tickets with independent work type, priority, and
  workflow state; conflict evidence is recomputed from the live rule, while browser-local scenario edits
  stay clearly separate from the shipped sample.
- **Click-to-inspect** — click any facility, ticket, or hex to read its attributes; hovering a
  conflicting facility flashes it on the map, and the detail panel re-centers on demand.
- **H3 screening** — the default workspace is a tunable **conflict-index** choropleth: a weighted,
  normalized score per hex (ticket volume, conflict rate, mean severity, facility density) with hotspot
  highlighting and click-to-drill-down into a cell's tickets.
- **Import & export** — import a KMZ/KML overlay and select one feature as the active AOI; export an
  inspected ticket to a styled **KMZ** with Ticket/AOI/conflict folders, legend text, and the exact rule
  assumptions.

## How it's built

DuckDB-WASM and a Rust→WebAssembly geometry module run in the browser, splitting query work from
precision geometry the way a PostGIS backend and a thin client would — but with no server:

| Concern | Component |
|---|---|
| Tabular + spatial **queries** — ticket/facility search, stats, AOI↔facility conflict join (`ST_Intersects`), jurisdiction point-in-polygon (`ST_Within`), envelopes | **DuckDB-WASM** + Spatial, querying the GeoParquet assets over HTTP range reads |
| **Precision geometry** — geodesic meter buffering (ellipsoidal circles via `geographiclib-rs`; lines/polygons via a UTM planar buffer), H3 multi-resolution indexing + hex density, KMZ/KML parsing | **`geokit`**, a Rust → WebAssembly module (this repo) |
| **Rendering + interaction** — vector map, layer styling, hover/click picking, the 4-block layout | **MapLibre GL** + React + TypeScript |

Rendering is a **modular, responsive** four-block workspace — a top search/filter strip, a left
master-detail panel, the center map, and a right tabbed tool palette — with collapsible side rails and
keyboard shortcuts on desktop, collapsing to a draggable bottom sheet on phones. Conflict gating is a
generic, **config-driven** owner/status rule ([`data/demo_config.json`](data/demo_config.json)) applied
as a SQL `WHERE`.

## Quickstart

```bash
# 1. Build the geokit WASM package (needed by the web app)
wasm-pack build packages/geo-engine --target bundler --out-name geokit

# 2. (Optional) rebuild the demo data — Austin, TX by default; --metro to change region
pip install duckdb h3 requests
python scripts/build_demo_db.py --metro austin        # writes ~0.5 MB of GeoParquet to apps/web/public/data/

# 3. Run the web app
cd apps/web && npm install && npm run dev              # http://localhost:5173
```

`npm run build` produces a static bundle in `apps/web/dist`; `npm run preview` serves it at the
GitHub-Pages base path. DuckDB-WASM and its spatial extension load from the jsDelivr / DuckDB extension
CDNs at runtime — the only network dependency; everything else is static.

## The `geokit` module

A Rust→WebAssembly geometry module built on mature, pure-Rust crates (no C deps → clean wasm build):
`geo` (planar buffer), `proj4rs` (WGS84↔UTM), `geographiclib-rs` (geodesic circles), `h3o` (H3),
`zip`+`kml`+`geojson` (KMZ).

```bash
cargo test  -p geokit    # native: geodesic buffer area/shape sanity checks + H3 indices vs the reference cell
cargo bench -p geokit    # criterion benchmarks
wasm-pack build packages/geo-engine --target bundler --out-name geokit   # -> packages/geo-engine/pkg
```

WASM API (TypeScript surface): `buffer_geojson`, `h3_index_point`, `h3_multi_res`,
`h3_cell_boundary_geojson`, `h3_hex_density_geojson`, `h3_polyfill`, `kmz_to_geojson`.

## Repository layout

```
packages/geo-engine/     # `geokit` — Rust→WASM geometry module (buffer / H3 / KMZ)
  src/core/              #   pure-Rust logic (native unit + golden tests, criterion benches)
  src/wasm.rs            #   wasm-bindgen shims (compiled only for wasm32)
scripts/build_demo_db.py # downloads public data + fabricates tickets → GeoParquet
scripts/record_demo.mjs  # captures the demo walkthrough over CDP; make_demo_gif.sh renders docs/demo.gif
apps/web/                # Vite + React + TypeScript app (map + DuckDB/geokit query layer)
apps/web/public/data/    # committed GeoParquet assets (facility/ticket/aoi/county)
data/demo_config.json    # generic conflict rule (owner/status gating)
```
